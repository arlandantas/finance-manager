## Objetivo
O Administrador convida por e-mail o membro "Sem acesso ao app"; o convite fica vinculado àquele cadastro. Aceitar é a US-094b.

## Contrato técnico
- Sem migração (`invitations.memberId` e `invitations_member_pending_uq` já existem).
- `POST /api/v1/members/{id}/invitations` (`withApi` role ADMIN, `Idempotency-Key`), corpo `.strict()` `{ email: string }` (e-mail Zod; 400). Serviço `createLinkedInvitation` em `familia/invitations/linked.ts`, nesta ordem, na transação:
  1. `lockFamilyAdmins(tx, ctx, true)`;
  2. membro `id` da família, `removedAt IS NULL`, `userId IS NULL`; senão 404 uniforme "Membro não encontrado.";
  3. `email = normalizeEmail`; `expireStale(email, now)`; `pendingEmail` preenchido e diferente => 422 `INVITATION_EMAIL_MISMATCH`;
  4. e-mail de membro ativo com conta => 409 `DUPLICATE_MEMBER`; `pendingEmail` de OUTRO cadastro => 409 `EMAIL_BELONGS_TO_OTHER_MEMBER`; convite `PENDING` não vencido para o e-mail (comum ou vinculado) => 409 `DUPLICATE_INVITATION`;
  5. cotas `assertInvitationQuota` + `assertInviterQuota` (429 `INVITATION_LIMIT`), só depois das recusas acima;
  6. `pendingEmail` vazio => `UPDATE members SET pendingEmail = email` na mesma transação (unique => 409 `EMAIL_BELONGS_TO_OTHER_MEMBER`);
  7. insere convite `role = MEMBER`, `memberId = id`, 7 dias, só hash do token; violação de `invitations_member_pending_uq` => 409 `DUPLICATE_INVITATION`;
  8. e-mail após o commit (`afterCommit`, falha => `FAILED`), mesmo `invitationEmail` (sem nome do cadastro nem contagens).
- Resposta = `CreateInvitationResponse` (mesmo DTO, `InvitationDTO.memberId: string | null` novo).
- Invariante: convite vinculado pendente => `invitation.email = member.pendingEmail`.
- SEC-061: `rotateInvitation` passa a gravar `INVITATION_RESENT` só com `{ invitationId, resendCount }` (vale para todos os convites). Reenviar, copiar link, cancelar e recusar usam as rotas existentes sem mudança.
- `getFamily`: `MemberDTO.pendingInvitation: { id, expiresAt } | null` só para ADMIN em sem conta (ADR-038 §6); a lista "Convites pendentes" não duplica o vinculado (filtra `memberId IS NULL`).
- UI (`familia-screen.tsx` + `invite-unlinked-drawer.tsx` novo): ação "Convidar" no menu do sem conta (só ADMIN), campo e-mail preenchido com `pendingEmail`, aviso "Quem aceitar assume o histórico de {nome}"; selo "Convite pendente" com Reenviar, Copiar link e Cancelar.
- Arquivos: `invitations/linked.ts`, `invitations/service.ts` (só SEC-061 e DTO), `invitations/repo.ts`, `familia/schemas.ts`, `familia/service.ts`, `familia/hooks.ts`, rota `members/[id]/invitations/route.ts`, `invite-unlinked-drawer.tsx` (+ `familia-screen.tsx`).

## Critérios de aceite
1. ADMIN convida o sem conta: 201, convite `memberId = id`, `pendingEmail` gravado se estava vazio; `GET /family` traz `pendingInvitation`.
2. MEMBER => 403; membro de outra família, removido ou com conta => 404 uniforme.
3. E-mail diferente do `pendingEmail` => 422 `INVITATION_EMAIL_MISMATCH`, nada gravado e cota intacta.
4. E-mail de membro com conta => 409 `DUPLICATE_MEMBER`; de outro cadastro => 409 `EMAIL_BELONGS_TO_OTHER_MEMBER`; segundo convite => 409 `DUPLICATE_INVITATION`; convite comum para o e-mail do cadastro segue 409 `EMAIL_BELONGS_TO_UNLINKED_MEMBER`.
5. Cancelar, expirar ou recusar zera `pendingInvitation` e permite convidar de novo; membro, `pendingEmail` e histórico intactos.
6. Reenvio (máx. 3), copiar link e tetos como na US-003; `FamilyEvent.changes` do reenvio não contém e-mail (teste busca o e-mail em `family_events`).
7. Corpo do e-mail e `/convite/[token]` não contêm o nome do cadastro (teste com o mailer de teste).
8. Concorrência (`Promise.all`): convidar x remover o cadastro => um vence, sem convite pendente para membro removido; dois convites simultâneos => um 201, um 409.
9. Testes: integração `us-094a-convite-vinculado.int.test.ts` (ACs 1-8), E2E `US-094a-*.feature` (convidar, selo, cancelar).

## Fora de escopo
- Aceitar (US-094b); editar/remover o e-mail (US-095); convite em massa; fundir membros.

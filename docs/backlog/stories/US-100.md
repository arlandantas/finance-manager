## Objetivo
Prever uma transferência entre duas contas, sem efeito nenhum até ser efetivada; efetivar cria a transferência real, desfazer a devolve a prevista. Telas na US-100b.

## Contrato técnico
- Migração (expand): enum `PlannedTransferStatus { PREVISTA EFETIVADA }`, tabela `planned_transfers` (ADR-037 §1) com FKs compostas `(familyId, fromAccountId|toAccountId|transferGroupId|authorMemberId)`, CHECKs `fromAccountId <> toAccountId`, `amountInCents > 0`, `(status='EFETIVADA') = (transferGroupId IS NOT NULL)`, excluída só se `PREVISTA`, `deletedAt/deletedByMemberId` juntos; único `(familyId, transferGroupId)`; índice `(familyId, status, dueOn)`.
- `previstas/transfer-schemas.ts`: `CreatePlannedTransferSchema` `.strict()` `{ fromAccountId, toAccountId, amountInCents: 1..9_999_999_999, dueOn: DateISO, description?: 2..100 }` (mesma recusa de origem = destino de `CreateTransferSchema`); `UpdatePlannedTransferSchema` = parcial + `version`; `RealizeSchema` `{ version, amountInCents?, occurredOn?: DateISO }`. `PlannedTransferDTO` `{ id, from {id,name,archived}, to {...}, amountInCents, dueOn, description, status, isOverdue, transferGroupId, version, author: MemberRef }`.
- `previstas/transfer-service.ts`:
  - criar: contas ativas da família (422 `INVALID_REFERENCE` com `path`); `dueOn` qualquer data (passada = atrasada). Nenhuma escrita no ledger.
  - editar/excluir: `version` (409 `VERSION_CONFLICT` "alterada por {nome}"), `EFETIVADA` => 422 `PLANNED_TRANSFER_REALIZED_LOCKED`; sem diferença => 200 sem subir `version`; exclusão lógica.
  - efetivar: `lockFamilySplit` → linha `FOR UPDATE` → `PREVISTA` (senão 409 `PLANNED_TRANSFER_ALREADY_REALIZED`) → conta arquivada => 422 `ACCOUNT_ARCHIVED_LOCKED` → `createTransferGroup(kind=TRANSFER, amount = body ?? previsto, occurredOn = body ?? hoje, description = descrição ?? "Transferência")` (data futura 422 `FUTURE_DATE_NOT_ALLOWED`) → `UPDATE ... SET status='EFETIVADA', transferGroupId WHERE id AND version AND status='PREVISTA'`; tudo ou nada.
  - `listPlannedTransfers({ status, period? })` (atrasadas primeiro, depois `dueOn`).
- `contas/transfers.ts` `undoTransferGroup`: ao final, se existe `planned_transfers` com esse `transferGroupId`, volta a `PREVISTA`, `transferGroupId = NULL`, `version + 1`, `updatedByMemberId` (mesma transação).
- Rotas: `planned-transfers/route.ts` (GET, POST), `[id]/route.ts` (GET, PATCH), `[id]/delete/route.ts`, `[id]/realize/route.ts`; POSTs com `Idempotency-Key`. Qualquer membro ativo (sem "Só meu").
- Arquivos: `schema.prisma`, `transfer-schemas.ts`, `transfer-service.ts`, `contas/transfers.ts` e as 4 rotas.

## Critérios de aceite
1. Prever R$ 1.000,00 de Itaú Lucas para Poupança Mariana em 05/12: `accountBalances`, `ledgerTotals`, `collectOpenPayables`, `computeSettlement` e Extrato idênticos antes e depois (teste de reconciliação).
2. Origem = destino, conta arquivada ou de outra família => recusado; nada gravado.
3. Efetivar com 950,00 em 03/12: transferência real de 950,00 (duas pernas), prevista `EFETIVADA` com o grupo; saldos mudam só pela transferência.
4. Desfazer a transferência devolve a prevista a `PREVISTA` (efetivável de novo).
5. Efetivada não edita nem exclui (422); dois "efetivar" simultâneos => um 200, outro 409, uma transferência só.
6. Falha no meio da efetivação (ex.: data futura) não grava grupo nem muda a prevista.
7. `isOverdue` = `PREVISTA` e `dueOn < hoje`.
8. Testes: integração `us-100-transferencia-prevista.int.test.ts` (ACs 1-7, isolamento por família).
